# NitroBoost — Engineering Update v1.23.0

**التاريخ:** 2026-10-24 · **الأساس:** v1.22.0 (versionCode 29) · **النتيجة:** v1.23.0 (versionCode 30)

هذا التقرير يوثّق العمل المنفذ فعليًا على المصدر: مراجعة شاملة، إصلاحات في الملفات نفسها،
اختبارات جديدة، ونتائج بناء حقيقية. كل إصلاح أدناه تم التحقق من وجود خلله في النسخة
الأصلية قبل تعديله — لم يُطبَّق أي إصلاح "احترازي" على كود سليم.

---

## 1. منهجية العمل

1. **استنساخ ومراجعة كاملة:** 134 ملف Kotlin مصدري + 46 ملف اختبار + Manifest + Gradle
   + CI workflow + assets. قرأتُ بنفسي: النواة (Journal، JournaledSystemExecutor،
   BoostEngine، ThermalGuard)، طبقة المنصة (AndroidExecutor، RootShell، ShizukuShell،
   NitroUserService، Monitor)، المحرك التكيفي (AdaptiveLoop كاملًا، SessionQualityGate)،
   AppStore، BoosterService، والمهام الحساسة. وكلّف وكيلا مراجعة مستقلين بفحص
   tasks/+platform/+math وservice/+ui/+data/assets، ثم أعدتُ التحقق شخصيًا من كل
   اكتشاف قبل قبوله.
2. **لا افتراضات:** قائمة الفحص الأولية للمستخدم عُوملت كقائمة فحص فقط. بعض البنود
   (مثل حقن الأوامر) فُحصت ووُجدت مغطاة أصلًا — انظر §5.
3. **إصلاح ثم قياس:** كل إصلاح تلاه تشغيل كامل للاختبارات والبوابات الثابتة.

## 3. الفحوصات التي وُجدت سليمة أصلًا (لم تُلمس)

- **حماية الحقن:** كل قيمة تُستوفى في أوامر مميزة تمر عبر `ShellInput` (حزم، sysfs،
  قيم إعدادات، tokens)؛ أوامر الاسترجاع المحفوظة عبر `safeRevertCommand` (قائمة سماح) —
  اختبار التلاعب موجود مسبقًا.
- **الحماية الحرارية:** أرضية 44/48/52°C خام + الحالة الحرارية + الميل التنبؤي معًا؛
  الفشل الحراري أثناء التجربة يوقفها ويتراجع فورًا (NonCancellable finally)؛ فقدان
  المستشعر أثناء تجاوز حراري نشط = فشل مغلق.
- **Journal وRollback الأساسيان:** كتابة كتابة-مسبقة قبل أي تعديل مدعوم، fsync قبل
  الاستبدال، `.bak`، تعافٍ من التلف، تخطي مدخل مجهول، ورفض متابعة الكتابة إذا تعذّر
  التسجيل الدائم (fail-closed).
- **بوابة جودة التجارب:** عينات غير مكتملة/قديمة/متقلبة/ملوّنة حراريًا لا تدخل الدليل
  أبدًا؛ تصحيح Bonferroni قبل اختيار فائز؛ لا ادعاء تحسين بلا قياس.

## 5. ما لم يُختبر (حدود صريحة)

1. **لا جهاز Android فعلي في هذه البيئة:** لم تُنفذ أي تجربة تثبيت/تشغيل على جهاز حقيقي.
   مسارات تشغيل Shizuku الفعلية، ربط الخدمة، وتنفيذ الأوامر المميزة على ROM حقيقي
   (خصوصًا Android 7.x لحالة H1) تتطلب جهازًا — حالة H1 مغطاة بمراجعة API-level
   موثقة (destroyForcibly أُضيف في API 26) ولم تُشغَّل فعليًا.
2. **لا توقيع إصدار:** لا توجد مفاتيح توقيع المشروع؛ المخرج **APK debug** قابل للتثبيت
   للتجربة، وليس إصدار release موقّع. لا تدّعي أنه غير ذلك.
3. **لا قياسات FPS/أداء:** لم تُنفذ أي benchmark لعب؛ لا يوجد ادعاء تحسن أداء ناتج عن
   هذه الإصلاحات — كل التغييرات تصحيحية/أمان.
4. **محاكاة deviceidle/game API في الاختبارات** تعتمد FakeExecutor (نمط المشروع الحالي).
5. **`AppOpsManager.checkOpNoThrow(String,…)` على API 24–28:** مغلّف بـtry/catch، لكن
   سلوك `NoSuchMethodError` إن حدث يحتاج جهازًا فعليًا للتأكيد — بقيت ضمن قائمة
   التحقق الميداني.

## 6. المشكلات المتبقية (مرتبة بالأولوية)

1. **تحقق ميداني مطلوب:** تثبيت APK debug على أجهزة API 24–25 (حالة H1)، وAPI 34+
   (نوع الخدمة specialUse)، وأجهزة OEM (HyperOS/ColorOS) لسيناريوهات الحظر.
2. **I/O على الخيط الرئيسي في واجهات معينة:** `HomeFragment.buildChips` يقرأ assets
   و`profiles_custom.json` في كل عرض تبويب (لا يسبب ANR عادة لكنه jank محتمل).
   اقتراح: ذاكرة مؤقتة للملفات المدمجة في ProfileStore.
3. **`BoosterService.onDestroy` يظل يحتفظ بالخيط الرئيسي** أثناء الاسترجاع المتزامن
   عند موت الخدمة (تصميم مقصود لضمان الاسترجاع قبل موت العملية، لكنه قد يصل ANR مع
   journal كبير — التخفيف الآمن يتطلب مهلة صريحة).
4. **حالة التعليق في "Boosting" عند فشل الاسترجاع دائمًا:** الزر يبقى معطلًا حتى نجاح
   الاسترجاع أو "Restore all" — يُقترح حالة UI صريحة "restore pending".
5. **عناصر ميتة شكلية:** `BoosterService.lastScore` تُكتب ولا تُقرأ؛
   `FpsOverlayService.blockedNoPermission` لا يقرأها أحد؛
   `widget_info.updatePeriodMillis=60000` (يقلّصه النظام إلى 30 دقيقة) — تنظيف اختياري.
6. **اختبار ذيل `GameApiTask` و`GovernorTask` عبر مسار المحرك** (كما فُعل لـio_scheduler)
   لتثبيت عقد الـjournal للمتغيرات المتعددة.

## 7. تعليمات تشغيل واختبار الإصدار الجديد

```bash
# بناء محلي (نفس بيئة هذا العمل)
cd NitroBoost
# لا يوجد gradle-wrapper.jar في المستودع (ملف ثنائي) — مرة واحدة:
gradle wrapper --gradle-version 8.14.3
./gradlew test              # 266 اختبار JVM
./gradlew assembleDebug     # APK في app/build/outputs/apk/debug/

# تثبيت APK debug على جهاز اختبار
adb install -r app-debug.apk   # أو بوصلة الملف مباشرة

# خطوات التحقق الميداني المقترحة
# 1. امنح Shizuku، شغّل جلسة على لعبة، ثم أوقفها وتأكد من إعادة القيم (Journal → Settings).
# 2. على Android 7.x: تسبب انتهاء مهلة أمر مميز (اترك نافذة منح Magisk >10ث) — لا يجب أن ينهار التطبيق.
# 3. فعّل "السطوع الذروة" (مستوى 3) على شاشة بنطاق واسع — يجب ألا يقل السطوع الحالي.
# 4. فعّل العائم دون منح صلاحية الرسم فوق التطبيقات ثم شغّل تحسينًا — يجب أن تظهر نافذة الشرح وتمر الجلسة.
# 5. اضغط ويدجت التحسين والتطبيق مفتوح بالفعل — يجب أن يبدأ تحسينًا.
```
