# مراجعة الهندسة العكسية والمقترحات — NitroBoost v1.22.0

**التاريخ:** 2026-10-17

**النطاق:** شيفرة NitroBoost، اختبارات JVM/Python، إعدادات Android وCI، والمرجع الثنائي RevBoost 1.8.1-debug الموجود في `reference/`.

## الملخص التنفيذي

المستودع يحتوي على تطبيق Android أصلي، لا مجرد APK: Kotlin + Material 3، ويشمل 21 مهمة تعزيز، ملفات ألعاب، قراءة telemetry، محرك تجارب A/B تكيفي، وحفظًا محليًا للتغييرات القابلة للعكس ثم استعادتها. المكوّن المرجعي في `reference/` هو تفريغ ثنائي لتطبيق آخر، وليس شيفرة NitroBoost.

أضيف في v1.22.0 دعم تثبيت Android 7.0 / API 24 مع الإبقاء على `targetSdk=36`، وحواجز إصدار النظام لقنوات الإشعارات وخدمات `SPECIAL_USE`، واستبدال اعتماد التخزين على `java.nio.file` غير المتاح قبل API 26. كما أُصلح اختلاف FPS الذي كان يقارن جلسات ألعاب مختلفة، فأصبحت المقارنة محصورة في آخر متوسط للعبة نفسها، وموسومة بوضوح بأنها رصدية وليست اختبار A/B أو إثباتًا سببيًا.

## منهج التحليل وحدوده

- تتبعت نقاط الدخول في `AndroidManifest.xml`، التطبيق والخدمات، `AppStore`، `BoostEngine`، `Journal`، منفذي النظام/Shizuku، طبقة القياس، ملفات Gradle، workflow والاختبارات.
- فُحصت ملفات RevBoost الثنائية محليًا: Manifest بصيغة Android binary XML، وDEX متعدد الملفات، وملفات profiles/resources. استُخدمت أسماء الفئات والسلاسل النصية كقرائن على البنية والميزات.
- **هذا تحليل ساكن أولي للـDEX/manifest وليس decompilation كاملًا أو تحليلًا ديناميكيًا.** لذلك لا تُعامل السلاسل النصية كإثبات أن كل ميزة تعمل كما يعلنها التطبيق، ولا تتضمن المراجعة تشغيل APK المرجعي.
- لم يُنسخ أي كود من التطبيق المرجعي ولم يُعد توزيعه.

## الخريطة المعمارية المستنتجة من شيفرة NitroBoost

1. **واجهة المستخدم:** `MainActivity` وواجهات Home/Boost/Profiles/Settings مبنية على Views وFragments، مع موارد عربية وإنجليزية.
2. **تدفق العمل:** `AppStore` يجمع الحالة ويرسل الأوامر؛ `BoosterService` يملك دورة الجلسة ومراقبة الحرارة وخروج اللعبة؛ `FpsOverlayService` يعرض قياسات اختيارية.
3. **مهام النظام:** `BoostEngine` يطبق المهام المستقلة بحسب الملف ومستوى التعزيز والقدرات المتاحة. Shizuku هو المسار المفضل، والـroot بديل اختياري.
4. **الاستعادة:** `Journal` يكتب نية الاستعادة قبل التغيير القابل للعكس، ويحفظ نسخة احتياطية، ثم يعيد التغييرات بترتيب عكسي. trim/force-stop أفعال أحادية الاتجاه ولا توصف بأنها قابلة للعكس.
5. **القياس:** monitor محلي يجمع ما يتاح من CPU/RAM/حرارة/بطارية/FPS/إطارات/شبكة؛ المصادر الغائبة تبقى null. قياس TCP ليس latency لخادم اللعبة، وGPU والطاقة لا يُختلقان عند غياب مصدر موثوق.
6. **التجارب التكيفية:** `AdaptiveLoop` و`AdaptivePolicy` و`DecisionLedger` تحفظ المقارنات المحكومة بجودة العينات والسياق والحرارة. لا تُستخدم نتيجة غير حاسمة كفوز.
7. **الاختبار والنشر:** اختبارات Kotlin للنواة، بوابات Python ساكنة/أمنية، وGitHub Actions للبناء والتحقق من APK. نشر GitHub Release محصور في `main`.

## ما تكشفه عينة RevBoost المرجعية

المرجع هو `com.revboost.app.debug` بالإصدار `1.8.1-debug`، ومكوّن من عدة ملفات DEX. تظهر أسماء/سلاسل الفئات إشارات إلى:

- `RevBoostController` و`BoostOrchestrator` وطبقات وحدات CPU/GPU والملفات؛
- `GameRepository` و`GameEditorActivity` وبيانات profiles مدمجة ومخصصة، مع أسماء تشير إلى مزامنة cloud profiles؛
- `PerformanceMonitor` و`ThermalReader` و`FpsOverlayService` وتقارير الجلسة؛
- `ShizukuManager` ومسار root، وخدمة تعزيز، وQuick Settings tile وwidget؛
- فحوصات capability/thermal guard ورسائل تحذير ومقترحات.

هذه قرائن على نطاق المنتج لا إثبات لسلامة أو فعالية تعديلاته. المقارنة العملية: RevBoost وNitroBoost يشتركان في profile/editor، overlay، مراقبة الأداء، Shizuku/root وبعض أدوات الجلسات. الفارق الأكثر قابلية للتحقق في شيفرة NitroBoost هو سجل الاستعادة الدائم، بوابات الحرارة، وتقييم A/B المحلي؛ ولا يوجد benchmark مستقل يثبت أن أيًا منهما أسرع على جهاز بعينه.

## النتائج التي عولجت

### 1. توافق Android 7.0 لم يكن حقيقيًا

- قبل التعديل: `minSdk=26`، وبالتالي لا يمكن تثبيت التطبيق على Android 7/API 24.
- كما استخدمت مسارات `Journal` و`DecisionLedger` و`ProfileStore` واجهات `java.nio.file.Files` التي تبدأ من API 26.
- استدعاء إنشاء notification channels كان غير محروس قبل API 26. وكان مسار الخدمة يمرر `FOREGROUND_SERVICE_TYPE_SPECIAL_USE` ابتداءً من API 29، رغم أن نوع الخدمة هذا متاح من API 34.
- **الإصلاح:** `minSdk=24` مع `targetSdk=36`، واستبدال عمليات move/copy بمسار ملفات من `java.io` يعمل داخل المجلد نفسه، وحراسة Notification Channels عند API 26 وSPECIAL_USE عند API 34. أُضيف فحص ساكن يتحقق من حدّ SDK وحراسات الاستدعاءات ويمنع رجوع اعتماد `java.nio.file` في شيفرة الإنتاج.

### 2. فروق FPS كانت تخلط ألعابًا مختلفة

- `KEY_PREV_FPS` كان قيمة واحدة مشتركة؛ لذا قد تقارن جلسة PUBG بجلسة Genshin أو ملف لعبة مختلف.
- **الإصلاح:** مخزن محلي محدد باسم الحزمة، مقيّد إلى 32 لعبة، واختبارات تمنع تسرب قيمة لعبة إلى أخرى. تقارير قديمة بلا `gamePackage` لا تعرض delta غير معروف المصدر. يوضّح النص أن الفرق وصفي وغير مضبوط، حتى بين جلستين للعبة نفسها.

### 3. الادعاء عن الأداء يحتاج حدودًا أوضح

لا تثبت الجلسات العادية تكافؤ المشهد أو الحرارة أو الإعدادات؛ لذلك لا يُعرض delta كبرهان على أن التعزيز «حسّن» FPS. المحرك التكيفي المقترن يظل المسار الإحصائي الأقوى، مع أنه لا يثبت تساوي workload الداخلي للعبة.

## التحقق

- `tools/verify.py`: فحص XML والموارد والمكونات ومراجع Kotlin وحدّ Android API.
- `tools/security_verify.py`: بوابة regression محدودة للأذونات والمكونات والتبعيات وworkflow؛ ليست تدقيقًا أمنيًا أو MASVS.
- `python3 -m unittest discover -s tools -p 'test_*.py' -v`: اختبارات أدوات Python.
- اختبارات Kotlin الجديدة: عزل baselines حسب الحزمة، حدّ 32 سجلًا، ونجاح/فشل الاستبدال الذري للملفات؛ أما SDK gates فتتحقق منها بوابة `tools/verify.py` الساكنة.
- لا يوجد Android SDK أو Java/Gradle في بيئة العمل المحلية؛ يلزم نجاح GitHub Actions (`test`, `lintDebug`, `assembleDebug`) قبل النشر. لا يوجد جهاز Android 7 فعلي أو benchmark لعب متاح هنا.

## قرار الإصدار

لا تُنشر نسخة APK على أنها release قبل نجاح CI والتحقق من أن داخل APK `minSdk=24` و`targetSdk=36`، توقيعها وبصمة SHA-256. وحتى بعد نجاح البناء، يوصف الملف غير الموقّع بمفتاح release بأنه **debug/testing APK** فقط. لا توجد في هذا المستودع أسرار توقيع؛ لا ينبغي إنشاء keystore بديل يغيّر هوية التحديث.
